# BharatPass code guide

This document explains what each project file does and how the complete application works. It is based on the code that is currently in the repository, so it also points out places where older reports no longer exactly match the implementation.

## 1. What the application is

BharatPass is a role-based digital bus/train pass system:

1. A passenger registers or logs in.
2. The passenger applies for a pass for a city and duration.
3. An administrator reviews and approves the application.
4. The passenger completes the payment flow.
5. The server activates the pass, creates its validity dates, and assigns a QR token.
6. The passenger requests a short-lived OTP and displays it inside a QR code.
7. A conductor scans the QR code or enters the OTP manually.
8. The server validates the pass and records the scan result.

The three user roles are `user` (passenger), `admin`, and `conductor`.

## 3. How the pieces connect

```text
Browser pages
  └─ public/js/app.js
       └─ fetch() requests
            └─ Express routes in server.js (local / deployed backend)
                 ├─ Mongoose models in models/
                 └─ MongoDB

Passenger dashboard ── payment UI ── /api/passes/activate
Passenger dashboard ── OTP request ── /api/qr/generate-otp
Passenger QR ── camera/manual OTP ── /api/conductor/scan ── ScanLog
```

Locally, `app.js` uses `http://localhost:3000` as the API base. In a deployed browser it uses relative `/api/...` URLs. Netlify rewrites those requests to the Render backend using [netlify.toml](netlify.toml). The standalone Netlify function in [netlify/functions/qr.js](netlify/functions/qr.js) is an alternate QR-generation endpoint for static/serverless deployment.

## 4. Backend: [server.js](server.js)

### Startup and configuration

- Loads environment variables with `dotenv`.
- Forces IPv4 DNS resolution to make MongoDB connections more reliable.
- Creates an Express app and reads `PORT`, defaulting to `3000`.
- Requires a real `MONGODB_URI`; placeholder or missing credentials stop the process.
- Connects to MongoDB through Mongoose with connection and socket timeouts.
- Loads all five Mongoose models.
- Enables CORS, JSON request bodies up to 10 MB, and static serving from `public/`.
- Starts listening and prints demo credentials.

`isMockMode` is set to `false`, so the active application uses MongoDB. The `mockData` object and mock branches are retained as old local-testing code but are not reachable unless that flag is changed.

### Database utilities

`GET /api/admin/seed` clears users and passes, creates hashed demo users, resets system settings, and inserts two demo passes. It is destructive and should only be used for development. In production it requires the `SEED_KEY` query parameter.

`GET /api/admin/fix-index` drops the old `qrToken_1` MongoDB index. It is an emergency migration helper for duplicate/null QR-token index problems.

### Authentication routes

`POST /api/auth/login` finds a user by email and compares the submitted password with the bcrypt hash. It returns only the user identity and role; the browser stores that response as a lightweight local session.

`POST /api/auth/register` checks for duplicate email, hashes the password with bcrypt, stores an optional base64 photo, and creates a user. The client currently submits the default `user` role.

There is no server-side session/JWT middleware. Role protection is currently implemented by the frontend's `requireAuth()` redirect, so this is a college-project/demo authentication design rather than production-grade authorization.

### Admin and pass routes

- `GET /api/admin/users` returns users sorted newest first.
- `GET /api/admin/stats` counts users, passes, active/pending passes, scan logs, and sums prices of active passes as revenue.
- `GET /api/passes?userId=...` returns all passes or one passenger's passes. It populates user name/email/photo, then flattens those values for the frontend.
- `POST /api/passes` creates a pending pass after validating that `userId` is a valid MongoDB ObjectId.
- `POST /api/admin/approve-pass` changes `pending` to `approved`.
- `POST /api/admin/reject-pass` changes a pass to `rejected`.
- `POST /api/passes/activate` changes an approved pass to active, calculates 30/90/365 days from its type, generates a cryptographically random 32-character hex token, and stores the payment ID.

The intended state flow is:

```text
pending ──admin approve──> approved ──payment/activation──> active ──date passes──> expired
   └────────admin reject──────────────────────────────────> rejected
```

### Settings routes

`GET /api/settings` reads the single settings document. If none exists, it creates defaults. `POST /api/admin/settings` updates cities and/or prices. These values control the choices shown in the landing page, user application form, and admin settings screen.

### OTP and QR validation routes

`POST /api/qr/generate-otp` verifies the pass belongs to the requesting user and is active, marks it expired if its end date has passed, then creates a six-digit OTP valid for 60 seconds. The OTP is stored in `Pass.currentOtp` and its expiry in `Pass.otpExpiresAt`.

`POST /api/conductor/scan` accepts one of these inputs:

- `passId + otp` from a QR scan;
- `otp` from manual entry; or
- `qrToken` for legacy token-based validation.

It finds the pass, checks active/expired status, checks and consumes a QR OTP when appropriate, creates a `ScanLog`, and returns the result plus passenger data. Possible results are `valid`, `invalid`, `expired`, `otp_expired`, and `otp_used`.

`GET /api/conductor/logs` returns the newest 100 scan logs.

`GET /api/qr` converts a JSON payload containing token, pass ID, city, and passenger name into a base64 PNG data URL using the `qrcode` package. This is a general QR image endpoint; the passenger dashboard also creates the final short-lived OTP QR directly in the browser.

`GET /api/health` returns `{ status: "ok", time: ... }` for deployment checks.

## 5. Database models

All model files import Mongoose, define a schema, and export a model. They describe MongoDB documents and validation rules.

### [models/User.js](models/User.js)

Stores account details: required `name`, unique required `email`, hashed `password`, optional base64 `photo`, role (`user`, `admin`, or `conductor`), and `createdAt`.

### [models/Pass.js](models/Pass.js)

Stores the pass owner, city, pass type, status, validity dates, price, payment ID, QR token, current OTP, OTP expiry, and creation date. `userId` references `User`; `qrToken` is unique and sparse so pending passes may exist without a token.

### [models/Payment.js](models/Payment.js)

Defines a payment document with pass ID, user ID, amount, status, and payment date. It is ready for a separate payment collection, but the current `server.js` does not create or read `Payment` documents. Current activation stores `razorpayPaymentId` directly on the pass.

### [models/ScanLog.js](models/ScanLog.js)

Stores each conductor validation: pass reference, conductor reference, time, result, passenger name, and city. This powers admin scan history and reporting.

### [models/SystemSettings.js](models/SystemSettings.js)

Stores the available cities and monthly/quarterly/yearly prices. The app expects one settings document and creates defaults when necessary.

## 6. Shared frontend: [public/js/app.js](public/js/app.js)

This script is loaded by the public, login, user, admin, and conductor pages.

- Theme code reads/writes `bharatpass_theme` and toggles `light-mode` on the document/body.
- `API_URL` chooses local `http://<host>:3000` or an empty production base.
- `fetchPasses(userId)` loads pass records.
- `apiPost(endpoint, data)` sends JSON POST requests and turns API errors into JavaScript exceptions.
- `getSession`, `setSession`, and `clearSession` manage `bharatpass_session` in browser localStorage.
- `requireAuth(role)` redirects unauthenticated users to login and redirects a logged-in user to the correct role dashboard.
- `generateId` and `generateToken` are legacy client-side helpers; active QR tokens are now generated securely on the server.
- `formatDate`, `formatDateTime`, `isExpired`, and `addDays` provide date helpers.
- `getPassDuration` and `getPassPrice` provide fallback client-side pricing.
- `getBadgeHTML` and `getBadgeTypeHTML` generate status/type badges.
- `showToast` creates and automatically removes notification messages.
- `initSidebar` fills dashboard user information.
- `logout` clears the session and returns to login.
- `initTabs`, `openModal`, and `closeModal` implement shared UI behavior.

The browser stores only session/theme preferences locally; users, passes, settings, and scan logs are fetched from the backend.

## 7. Frontend pages

### [public/index.html](public/index.html)

The public landing page. It contains the navigation bar, hero section, “how it works” explanation, feature cards, pricing cards, and calls to login/register. Its small inline script redirects already logged-in users to their role dashboard and loads current city/pricing settings from `/api/settings`. It uses [public/css/style.css](public/css/style.css) and the shared theme script.

### [public/login.html](public/login.html)

The common authentication page. It has Login and Register tabs.

- `switchTab` changes the active form.
- `handleLogin` calls `/api/auth/login`, saves the returned user session, and redirects by role.
- `handleRegister` submits name, email, password, role, and optional photo to `/api/auth/register`.
- `openCamera`, `capturePhoto`, and `handlePhotoFile` acquire a selfie from the webcam or file picker, crop it with a hidden canvas, and store it as a base64 preview.
- Error helpers show validation/API errors.

### [public/user/dashboard.html](public/user/dashboard.html)

The passenger dashboard has My Passes, Apply, and Payments areas.

- Checks `requireAuth('user')` on load.
- Loads settings and the passenger's passes.
- Lets the passenger choose a city and monthly/quarterly/yearly plan.
- `handleApply` creates a pending pass through `/api/passes`.
- Approved passes can be paid through the Razorpay Checkout script. The UI supports mock payment fallback behavior.
- `activatePassAfterPayment` calls `/api/passes/activate` with the returned payment ID.
- `showQR` requests a fresh OTP, builds a QR payload containing pass ID and OTP, and displays a QR image with a 60-second countdown. The browser QR library is loaded from jsDelivr.
- It renders pass status, validity dates, price, and renew/payment/QR actions.

The page includes the Razorpay checkout script and a QRCode browser library. Payment activation is still finalized by the backend route.

### [public/admin/dashboard.html](public/admin/dashboard.html)

The admin control panel uses Tailwind CDN classes plus its own inline dashboard logic.

- Checks `requireAuth('admin')`.
- `fetchAllData` loads settings, all passes, users, logs, and statistics.
- `renderOverview` displays summary cards.
- `renderPasses` and `filterPasses` show passes by status and offer approve/reject actions.
- `renderUsers` shows registered accounts and photos.
- `renderScanLogs` shows conductor validation history.
- `renderSettings`, `addCity`, `removeCity`, and `savePrices` manage cities and prices.
- `approvePass` and `rejectPass` call the corresponding admin routes.
- `resetDB` calls the destructive seed endpoint to recreate demo data.
- The page has a custom theme-toggle wrapper and its own toast implementation.

### [public/conductor/scanner.html](public/conductor/scanner.html)

The conductor interface has Scanner, History, and Profile sections.

- Loads `html5-qrcode` from a CDN for camera scanning.
- Checks `requireAuth('conductor')`.
- `startScan` asks for camera permission and starts QR decoding.
- `onScanSuccess` receives decoded text and passes it to `processTokenString`.
- `processTokenString` parses the QR JSON, extracts pass ID/OTP, and calls `/api/conductor/scan`.
- `processManualOtp` supports entering an OTP without the camera.
- `showResult` presents valid, invalid, expired, OTP-expired, and OTP-used outcomes, including the passenger photo when available.
- `renderHistory` and `updateScanCount` load scan logs from the server.
- `stopScan` closes the camera scanner; `closeResult` dismisses the result panel.

### [public/css/style.css](public/css/style.css)

The shared stylesheet defines CSS variables, dark/light theme colors, typography, navigation, buttons, forms, cards, badges, stats, tables, modals, toast notifications, dashboard layout, QR/pass cards, scanner results, and responsive breakpoints for tablets and phones. It is presentation-only; it does not contain business logic.

### [public/_redirects](public/_redirects)

Contains Netlify rewrite rules. `/api/*` is proxied to `https://bharatpass.onrender.com/api/:splat`; every other path falls back to `index.html` for the single-page hosting behavior.

### [public/images/logo.jpeg](public/images/logo.jpeg) and [public/images/favicon.jpg](public/images/favicon.jpg)

Static branding assets referenced by the HTML pages. They do not contain executable code.

## 8. Deployment/configuration files

### [package.json](package.json)

Defines the project as `bharatpass`, uses `server.js` as the entry point, and provides `npm start`/`npm run dev` (both run `node server.js`). Runtime dependencies are Express, Mongoose, CORS, dotenv, bcryptjs, and qrcode. `mongodb-memory-server` is listed as a development dependency but is not used by the current source files.

### [package-lock.json](package-lock.json)

Generated by npm. It locks the exact dependency tree so teammates and deployment servers install compatible versions. It should normally be updated by npm, not edited manually.

### [netlify.toml](netlify.toml)

Publishes `public/`, discovers functions in `netlify/functions`, uses port 8888 for Netlify Dev while targeting the Express server on 3000, and defines the production API/static redirects.

### [render.yaml](render.yaml)

Defines the recommended Render deployment: a Node web service using `npm install` and `npm start`, a health check at `/api/health`, `NODE_ENV=production`, and a secret `MONGODB_URI` that must be entered in Render rather than committed to the repository.

### [netlify/functions/qr.js](netlify/functions/qr.js)

Netlify-compatible version of QR generation. It handles CORS and OPTIONS requests, reads query parameters, serializes token/pass/city/passenger/validity/status information as JSON, and returns a QR PNG data URL. It does not connect to MongoDB or validate a pass; it only generates an image.

## 10. Important implementation notes

- The current source uses MongoDB, not localStorage, for application data. LocalStorage is used for browser session and theme only.
- The frontend redirects based on role, but the API does not currently enforce roles with server middleware. A production version should add authenticated tokens/sessions and authorization checks to admin/conductor endpoints.
- The Razorpay checkout is integrated in the browser, but the server does not verify a Razorpay signature. A production payment flow should verify payment server-side before activation.
- `Payment.js` is currently unused by the routes. Either create Payment records during activation or remove the unused model after deciding on the final data design.
- The seed and fix-index endpoints mutate database structure/data and should be protected or removed before a public production release.
- Prices are duplicated as frontend fallback values and backend settings. Admin settings are fetched at runtime, but a more centralized pricing strategy would avoid mismatches.

## 11. Running the project

1. Install Node.js and MongoDB Atlas access.
2. Run `npm install`.
3. Create a `.env` file with a valid `MONGODB_URI` and, for production seed protection, `SEED_KEY`.
4. Run `npm start`.
5. Open `http://localhost:3000`.
6. Use the seed endpoint from the admin dashboard or call `/api/admin/seed` during development.
